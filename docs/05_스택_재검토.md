# 주요 스택 재검토

- 작성일: 2026-11-10
- 검토 대상: `04_기술스택_및_구조.md`의 D4(벡터DB), D5(임베딩), D10(DB), D11(트레이싱), 그리고 LLM 호출 구조(D3, D8)
- 검토 기준: ① 내 서비스의 실제 규모와 특성에 맞는가 ② 근거가 논리적인가 ③ 더 단순한 대안은 없는가

## 0. 서비스 특성 (판단의 전제)
- 사용자 1명, 데이터는 개인 노션 수백~수천 페이지 → 조각(chunk)은 대략 1만~5만 개 수준
- **한국어와 영어가 섞인 기술 메모**: 고유명사, 코드, 명령어가 많습니다. 예: `torchrun`, `OOM`, `yolo26`
- 질의 유형 두 가지:
  - 의미형: "그때 왜 그렇게 결정했지?"
  - 정확 매칭형: "학습 서버 접속 계정이 뭐였지?"
- 쓰기 작업이 있어 **안전성**이 중요합니다.

→ 결론적으로 **규모는 작고, 하이브리드 검색과 안전성이 핵심**인 서비스입니다.

## 1. 벡터DB: Qdrant → **유지** (근거를 바로잡음)

| 후보 | 하이브리드 검색 | 한국어 키워드 검색 | 운영 부담 | 평가 |
|---|---|---|---|---|
| **Qdrant** | dense + sparse, 서버 쪽에서 RRF로 결과 결합 | bge-m3의 학습된 sparse 벡터 사용 → **한국어 형태소 분석기가 필요 없음** | Docker 1개, 또는 로컬 파일 모드 | ✅ |
| Chroma | 오픈소스판의 sparse·하이브리드 지원이 제한적 | 약함 | 매우 낮음 | 기준선 용도로만 적합 |
| pgvector + Postgres | 가능 | Postgres 기본 전문검색에 **한국어 토크나이저가 없음** | 중간 | 다중 사용자 단계에서 재검토 |
| SQLite + sqlite-vec + FTS5 | 직접 구현 필요 | FTS5 trigram으로 우회 가능 | 매우 낮음 (파일 1개) | 단순하지만 직접 짜야 할 것이 많음 |
| LanceDB | 가능 (FTS 내장) | 토크나이저 이슈 있음 | 낮음 (임베디드) | 대안으로 가능 |

- **기존 근거 중 "운영 환경과 같은 구성"은 약한 근거였습니다.** 1만~5만 개 규모에서 성능은 어떤 DB든 차이가 없습니다.
- **진짜 근거는 한국어 하이브리드 검색입니다.** 한국어 키워드 검색(BM25)은 형태소 분석기가 필요해서 까다롭습니다. bge-m3 sparse 벡터를 Qdrant에 그대로 넣으면 이 문제를 피하면서 정확 매칭형 질의에 대응할 수 있습니다.
- 메타데이터 필터(날짜, 태그, 페이지 경로)도 기본 지원합니다.
- 보완: Qdrant에는 **로컬 파일 모드**(`QdrantClient(path=...)`)가 있습니다. 개발 초기에는 Docker 없이 시작하고, 같은 코드로 서버 모드로 전환할 수 있습니다.

## 2. 임베딩: bge-m3 → **기준선으로 유지하고, 비교 실험을 계획에 넣음**

| 후보 | 장점 | 단점 |
|---|---|---|
| **bge-m3** | 다국어, 최대 8192 토큰, **dense와 sparse를 한 번에 생성**, fp16 약 2GB | 최신 모델보다 dense 품질이 낮을 수 있음 |
| KURE-v1 (bge-m3를 한국어로 추가 학습) | 한국어 검색에 특화 | sparse 출력 여부 확인 필요 |
| Qwen3-Embedding (0.6B/4B) | 다국어 벤치마크 상위, 긴 문맥 | **sparse 없음**, 4B는 VRAM 부담 |
| multilingual-e5-large | 검증된 모델 | 최대 512 토큰 |

- bge-m3는 **Qdrant 하이브리드 검색과 짝이 맞는다**는 점에서 선택이 합당합니다.
- 다만 "가장 좋은 임베딩"이라고 단정할 근거는 없습니다. 그래서 **F6 평가에서 bge-m3, KURE-v1, Qwen3-Embedding-0.6B를 같은 평가셋으로 비교**하는 실험을 넣었습니다. 이 비교표 자체가 어필 포인트가 됩니다.
- 위 모델들의 성능 우열은 내 데이터로 측정하기 전까지 가정으로 둡니다.

## 3. DB (상태 저장): SQLite → **유지, 단 일관성 설계를 추가**
- 사용자 1명, 쓰기 경합 없음 → SQLite로 충분합니다. LangGraph도 공식 SQLite checkpointer를 제공합니다.
- **새로 발견한 문제:** SQLite(동기화 상태)와 Qdrant(벡터)는 서로 다른 저장소라 하나의 트랜잭션으로 묶이지 않습니다. 동기화 도중 실패하면 두 저장소의 상태가 어긋날 수 있습니다.
  - 대응 1: 조각 ID를 `hash(page_id, chunk_index, content)`로 **결정적으로 만들어 upsert가 멱등**이 되게 합니다.
  - 대응 2: 페이지 단위로 "Qdrant 반영 완료 → SQLite 커밋" 순서를 지킵니다. 실패하면 다음 동기화에서 다시 처리합니다.
- 다중 사용자 단계(2차)에서는 Postgres로 전환을 검토합니다.

## 4. 트레이싱: Phoenix → **유지, 단 계측 범위 한계를 발견**
- 경량이고 로컬에만 저장된다는 근거는 타당합니다.
- **한계:** 우리는 LangChain ChatModel이 아니라 `claude -p` 서브프로세스를 호출합니다. 그래서 자동 계측은 **LangGraph 노드 단위까지만** 잡힙니다.
  - LLM 호출 span은 직접 작성해야 합니다 (프롬프트, 응답, 지연시간, 비용 정보).
  - `claude -p` 안에서 일어나는 MCP 도구 호출은 바깥에서 보이지 않습니다. `--output-format stream-json`으로 이벤트를 받아서 span으로 변환해야 합니다.

## 5. ⚠️ 가장 중요한 발견: `claude -p`와 MCP 쓰기 도구의 결합은 위험함

기존 설계(D8)는 `claude -p --mcp-config`에 노션 공식 MCP를 연결하는 방식이었습니다. 이 경우:
1. **도구 실행 루프를 Claude Code가 소유합니다.** 노션 쓰기 도구를 넘기면 Claude가 그 안에서 바로 쓰기를 실행할 수 있고, **LangGraph의 승인 절차(interrupt)를 우회합니다.** R11(안전한 실행) 요구사항과 정면으로 충돌합니다.
2. 도구 호출 로직이 내 코드가 아닌 Claude Code 안에 있습니다. 그래서 "Tool calling을 직접 구현했다"고 말하기도 어렵습니다.

**수정한 설계:**
| 작업 | 누가 실행 | 방식 |
|---|---|---|
| 검색 (my-memory) | **내 코드 (LangGraph 노드)** | Retriever 노드가 직접 호출합니다. 매번 해야 하는 일은 LLM에게 맡기지 않습니다. |
| 다음에 무엇을 할지 결정 | LLM | `claude -p`를 **도구 없이** 호출하고, JSON 형식의 행동 계획을 받습니다. 내가 짠 ReAct 루프로 실행합니다. |
| 노션 읽기 | 내 코드 또는 읽기 전용 MCP | 허용 목록에 있는 도구만 씁니다. |
| **노션 쓰기** | **내 코드, 사용자 승인 후에만** | LLM은 변경안(JSON)만 만들고, interrupt 승인 → `notion-client`로 실행합니다. |
| MCP 서버 `my-memory` | 직접 구현 (유지) | Claude Desktop이나 Claude Code에서 **내가 직접 쓰는 도구**로도 활용하고, MCP 구현 역량을 증빙합니다. |

이렇게 바꾸면 tool calling 루프, 승인, 트레이싱이 모두 **내 코드 안에** 있게 됩니다. 어필할 수 있는 범위와 안전성이 둘 다 좋아집니다.
- 구현할 때 확인할 것: `claude -p`에서 내장 도구를 끄는 옵션(`--tools`, `--disallowedTools` 등)과 시스템 프롬프트를 교체하는 옵션이 실제로 동작하는지 F0에서 검증합니다.

## 6. 그 외
- **uv + Python 3.12:** 유지합니다.
- **torch + RTX 5080:** CUDA 12.8 이상 빌드(cu128 인덱스)가 필요합니다. FlagEmbedding이 요구하는 transformers 버전과 충돌할 수 있으니 F0에서 가장 먼저 검증합니다.
- **LangGraph:** 유지합니다. checkpointer와 interrupt가 위 수정 설계의 핵심입니다.
